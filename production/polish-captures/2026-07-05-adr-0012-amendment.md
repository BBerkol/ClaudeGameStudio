## Proposed change

Amend Accepted ADR-0012 with three clarifications forced by Phase 2.5 parts progression axis + ADR-0017 (multi-chassis + Bodywork + chassis-agnostic parts):

1. **Universal sum-of-parts armor rule reaffirmed with Bodywork.** ArmorContribution valid across all 7 SlotKind values (Weapon/Engine/Mobility/Hull/Armor/Exposable/Bodywork). armor_0 remains the whitelisted aggregator that ignores its own ArmorContribution.
2. **`InstallPart(string, int, int armorContribution = 0)` default parameter REMOVED.** ADR-0012 originally called this "not a primary/compat pair — both first-class permanent APIs." That framing becomes semantically wrong once non-zero ArmorContribution becomes common across all slot kinds under the parts progression axis. Every int-overload call site must pass ArmorContribution explicitly. Compile error at every unmigrated call → forces coverage.
3. **Enemy narrowing statement clarified as ADR-0015 pattern.** Enemies stay code-authored via the int overload. "Author 0 on most slots, non-zero only on hull_0 or exposable_N" is an authoring convention (data-side narrowing per ADR-0015), NOT a runtime branch. Runtime sum-of-parts recompute stays universal.

Amendment lands as an appended `## Amendment (2026-07-05)` section on ADR-0012 (inline convention per ADR-0010's 2026-05-30 Amendment). ADR statuses stay "Accepted" but with the amendment banner.

## Final-game picture this serves

At 1.0, every part on every slot potentially contributes to the vehicle's armor buffer (Reinforced Bumper adds armor, Heavy MG doesn't but could, Bodywork Visor adds cosmetic + small armor tick). The originally-shipped `armorContribution = 0` default parameter silently drops contributions if a call site is written pre-parts-axis-awareness and just uses the 2-arg form. Under the parts axis, that silent drop is catastrophic — a Bodywork part that should contribute 3 armor could be authored with a call that dropped its contribution, and no compile error or test failure surfaces the drift. Removing the default forces every call site to state the ArmorContribution explicitly.

The three fullscreen UIs (Inventory / Deck / RunMap) and the Codex depend on ArmorContribution being reliably computed from the parts list — any silent-drop path in `InstallPart` breaks the Inventory stat-total display and the Codex rarity progression.

## Technical Director Review

**Verdict:** APPROVE
**Spawned at:** 2026-07-05 (folded from Round 4 verdict on ADR-0017 — the amendment was a Round 4 required output, not a separate consult)
**Agent transcript:** (Round 4 verdict pasted in `2026-07-05-adr-0017-multi-chassis.md`; the ADR-0012 amendment is downstream of that verdict's A6 + atomic-commit requirement)

**TD reasoning summary:**

- **The default-param is a semantic trap that widens under the parts axis.** ADR-0012 §2 explicitly framed the default as "first-class permanent API." That framing was correct WHEN ArmorContribution was near-zero on most slots (M1 shape, per `feedback_unified_boss_armor_pool` — only Frame carried armor). Under the parts axis, non-zero contributions become common across all slot kinds. The default now silently drops contributions if a call site is written without parts-axis awareness. This is the exact "GDD verb signature not load-bearing" failure mode (`feedback_gdd_verb_signature_not_load_bearing`).

- **Compile error at every 2-arg site is the migration mechanism.** No hidden call sites survive. TestVehicleFactory helper (`Assets/Tests/EditMode/Combat/Helpers/TestVehicleFactory.cs`, 6 calls) is a natural funnel — updating it covers many test suites indirectly if the factory abstracts the call.

- **Universal rule + enemy narrowing reaffirmation is doc-only.** Runtime already treats sum-of-parts as universal (`Vehicle.RecomputeArmorPool` iterates all non-Offline slots without filtering by SlotKind). ADR-0012 §1 already stated "ArmorContribution is permitted on every SlotKind" — the amendment just re-affirms this with Bodywork explicitly listed as the 7th SlotKind. Not a rule change, a clarification.

- **Enemy narrowing statement (ADR-0015) closes a subtle ADR-0011 drift.** Enemies use the int overload with 0 on most slots — this is an authoring convention. Without explicit ADR-0015 framing, a future reader might see "enemies always use 0 armorContribution on Weapon/Engine/Mobility" as a code-side rule and try to enforce it in `Vehicle.InstallPart` (bimodal path violation of ADR-0011). Amendment states it's authoring-side only.

- **Timing:** Amendment lands in the Phase 2.5A atomic commit alongside ADR-0017 flip to Accepted. Both ADR statuses update in the same commit.

- **No new alternatives to consider.** ADR-0012 already exhausted the alternatives during its Accepted decision (2026-06-02). This amendment is a narrow signature change + doc reaffirmation, not a new architecture decision.

**Verdict shape:** APPROVE. Land the amendment in the Phase 2.5A atomic commit. ADR-0012 Status stays "Accepted" with a "Last Verified" bump and an appended `## Amendment (2026-07-05)` section.
