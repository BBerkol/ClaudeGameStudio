# Sweep A — ADR-0011 No-Bridges Violations

## Executive Summary

Codebase is mostly ADR-0011 clean: no `IsLegacyMode`, no `LegacyKindBridge`,
no duplicate `SlotKind` enums, no `_new/_old` parallel storage, no `[Obsolete]`
compat surface. The two real violation clusters are (a) an armor-contribution
default-param overload on `SlotInstance.InstallPart` / `Vehicle.InstallPart`
whose xmldoc explicitly names "legacy / test paths that pass bare ints" as
the reason it exists (pattern #5, ADR-0011 explicit prohibition), and (b) a
family of `BuildLegacy` / "if prefab not authored, construct programmatically"
fallbacks across ~14 CombatView widgets (pattern #3 bimodal + pattern #7
transitional comments). The remaining hits are stale xmldoc wording left over
from the ADR-0010 slot-system retirement (references to "legacy mode" / "layout
mode" / "Frame pool in legacy mode") — pattern #7 doc-side drift, not code
drift. Save.Adapters namespace is a legitimate live-model→wire-DTO projection
and is **exempt** (the adapter code itself invokes ADR-0011 as the reason it
exists as a split rather than a bimodal DTO).

Total classification: **2 BLOCKERS**, **3 CLEANUP clusters**, **1 EXEMPT cluster**.

## 1.0 BLOCKERS (must fix)

### B1 — `InstallPart` armor-contribution overload names legacy callers in xmldoc

**Pattern**: #5 (Backwards-compat constructor or method overloads).

- `Assets/Scripts/Combat/SlotInstance.cs:80-90`
- `Assets/Scripts/Combat/Vehicle.cs:271-274` (delegating overload)

Snippet (SlotInstance.cs):

```csharp
/// Optional <paramref name="partId"/> / <paramref name="displayName"/> carry
/// the installed part's identity for HUD use (ADR-0012); both default
/// to null for callers that don't have a part record (legacy / test
/// paths that pass bare ints).
public void InstallPart(int maxHp, int armorContribution = 0,
    string partId = null, string displayName = null)
```

Same "bare ints" phrase reappears in `VehicleBarStack.cs:983`:

```csharp
// Falls back to the SlotKind category label ("Weapon" / "Engine")
// when no part identity was supplied at install time (e.g. armor_0
// buffer, or tests that pass bare ints).
```

**Why it violates ADR-0011**: ADR-0011 §"Forbidden patterns at done state"
line 5 explicitly forbids "extra signatures preserved only so old call sites
compile." The xmldoc is a signed confession that the default-param exists for
legacy/test call sites. This is the exact "compat overload" pattern named in
the ADR. It also matches the user's own memory
`feedback_default_param_overload_semantic_trap.md` — default-param compat
preserves source compatibility, not semantics.

At 1.0, every `InstallPart` caller either has a `PartDefinitionSO` (player
vehicles) or is explicitly the enemy path where `armorContribution` is meaningfully
zero (memory `feedback_unified_boss_armor_pool.md` — enemies pool armor on Frame).
Neither case needs a defaulted parameter; both should pass explicitly. Tests
should either pass explicit `armorContribution: 0` or ship a `PartDefinitionSO`
fixture.

**Recommended fix**:
1. Drop the default value on both overloads. Force explicit `armorContribution:`
   at every call site (~1 file each in Scripts; ~N test files — count on demand).
2. Delete both "legacy / test paths that pass bare ints" phrases from the xmldocs.
3. Simultaneously update `VehicleBarStack.cs:983` fallback comment so the reasoning
   is not framed around a legacy caller shape.
4. This is a canonical ADR-0011 retirement slice: single ADR-0010-style six-phase
   template. CI grep gate: fail build on regex `bare ints|legacy / test paths`.

Severity: **1.0 BLOCKER**. It's the exact pattern the ADR calls out, in
production combat code, and it will be regressed the next time a designer
adds a chassis part unless the default is removed.

### B2 — `TEMP 2026-06-02` in `Dredge.FrameArmorHp = 0`

**Pattern**: #7 (Transitional comment; "TEMP"/"for now").

- `Assets/Scripts/Combat/Archetypes/Dredge.cs:91-96`

Snippet:

```csharp
/// TEMP 2026-06-02: dropped to 0 for playtest — currently impossible
/// to drain the armor pool before dying. Restore to 60 once the player
/// has the tools (Plate management, strip-disable pacing) to chew
/// through it. Tracked in session-state.

```

**Why it violates ADR-0011**: Explicit `TEMP` marker with a "restore later"

**Recommended fix**: Decide the shipping value with combat balance now — either
raise back to 60 (with the Plate/strip pacing arriving in the same slice) or
delete the field entirely and remove armor_0 from the Dredge layout if the
final answer is "Dredge has no armor pool." Delete the TEMP comment. This
is a small design + code slice, not a code-only fix.

Severity: **1.0 BLOCKER** — content-shape landmark, and every reader of Dredge
code is currently told "this number is wrong on purpose."

## 1.0 CLEANUP (should fix)

### C1 — `BuildLegacy` bimodal fallback across CombatView widgets

**Pattern**: #3 (Bimodal code paths) + #7 (transitional comments).

Files (~14 widgets share the shape):

- `CombatView/CardWidget.cs:182,190`
- `CombatView/AmbushBannerWidget.cs:30,33`
- `CombatView/BuffTooltipWidget.cs:79,88,113`
- `CombatView/BuffIconWidget.cs:36,37,66,72` (`WireLegacyRefs`)
- `CombatView/BuffStripWidget.cs:131,136,149,150,176` (`BuildIconLegacy` + `WireLegacyRefs`)
- `CombatView/CombatLogWidget.cs:48,51`
- `CombatView/CombatHud.cs:171,1144,1462,1490,1546,1581,1620,1665,1668,1720`
- `CombatView/DamagePopupWidget.cs:45,54`
- `CombatView/DamagePopupSpawner.cs:50,84,85,86` (`BuildPoolLegacy`)
- `CombatView/DebugStatsWidget.cs:39,42`
- `CombatView/EndTurnButton.cs:30,32,36,39`
- `CombatView/EnergyOrbWidget.cs:33,41`
- `CombatView/PileCountWidget.cs:79,131`
- `CombatView/ResourceBarWidget.cs:38,44`
- `CombatView/TurnPhaseWidget.cs:38,41`

Snippet (representative — CardWidget.cs):

```csharp
private void Awake()
{
    _rect = GetComponent<RectTransform>();
    if (_background == null) BuildLegacy();     // <-- pattern #3 bimodal
    ...
}

private void BuildLegacy()                       // <-- pattern #7 name
{
    _background = gameObject.AddComponent<Image>();
    ... [~50 lines of programmatic construction] ...
}
```

**Why it violates ADR-0011**: The shape is "if the prefab authored the child
tree, skip; otherwise construct the same tree programmatically." Two code
paths for the same runtime shape — pattern #3. The method name `BuildLegacy`
itself is a pattern #7 marker; comments across CombatHud.cs say things like
"Legacy path keeps the old 'AddComponent on ...'" and "Wave 7: legacy path
Instantiates _cardPrefab so the dimensions... match the authored Card.prefab
instead of being a stripped-down GameObject + AddComponent." The programmatic
path exists to avoid re-authoring prefabs during dev; at 1.0 every prefab is
authored and the fallback becomes dead code.

**Why CLEANUP and not BLOCKER**: The bimodal check is `if (_background == null)`
— when prefabs are authored (which the CombatPrefabAuthor pipeline guarantees
at 1.0 per memory `feedback_pre_author_bake_hook.md` + `project_combat_scene_architecture.md`),
the fallback is never called. Runtime is single-path. Impact is *reader cost +
dead-code risk*, not runtime bimodal behaviour. Still a real ADR-0011 violation
because the rule targets "done state code," not just live paths.

**Recommended fix**: Retirement slice for the CombatView widget layer, after
current polish captures settle:
1. Confirm every widget's authoring path is stable (CombatPrefabAuthor mounts
   all fields, memory `feedback_re_author_combat_after_vehicle.md` protocol).
2. Delete every `BuildLegacy` method + `if (_field == null)` guard.
3. Fail-fast at `Awake()`: `Debug.LogError("Widget X not authored — re-run Author Combat HUD Prefab")` + `return`.
4. CI grep gate: fail build on `BuildLegacy|WireLegacyRefs|BuildPoolLegacy|BuildIconLegacy`.

Severity: **1.0 CLEANUP**. Best folded into a single "CombatView legacy-fallback
retirement" slice, not per-widget.

### C2 — Slot-system-retirement doc drift in xmldoc

**Pattern**: #7 (transitional comments — "legacy mode" / "layout mode" wording
left behind after ADR-0010 landed 2026-06-02).

- `Assets/Scripts/Combat/CardEffectOutcome.cs:43-45` — `"legacy mode … layout mode"`
- `Assets/Scripts/Combat/DamagePipeline.cs:5-6` — `"vehicle-wide Frame pool in legacy mode; the R_ARM Armor slot in canonical mode"`
- `Assets/Scripts/Combat/DamagePipeline.cs:94` — `"legacy 'Status ignores reactive defences' rule"`
- `Assets/Scripts/Combat/SlotInstance.cs:108-110` — `"differs from the legacy 50%-of-MaxHp rule"`
- `Assets/Scripts/Combat/DamagePipeline.cs:45` — `"Plating retired 2026-05-28 with ADR-0009 migration"` (historical, but reinforces the pattern)
- `Assets/Scripts/CombatView/BuffTooltipWidget.cs:166` — `"legacy formatting still reads"`
- `Assets/Scripts/CombatView/RunSceneHost.cs:632` — `"legacy branch attaches StandaloneInputModule"`

**Why it violates ADR-0011**: ADR-0011 Validation Criteria (line 222) says:
"No ADR carries 'transitional' / 'bridge' / 'for now' comments in its decision
section at milestone-done." The code-side equivalent is xmldoc that
frames the current single-path world as "canonical mode" vs an implied "legacy
mode" — that framing tells the reader a bimodal path exists when it does not.
Per memory `project_adr_0010_complete.md`, the slot-system retirement merged
2026-06-02 (80b0cbe); these xmldocs are stale. `RunSceneHost.cs:632` is the
one where "legacy" refers to a live conditional — worth a targeted read to
confirm it's a Unity-side StandaloneInputModule / EventSystem check (may be
legitimate Unity 6.3 compatibility, not slot-system legacy).

**Recommended fix**: Doc-scrub pass — rewrite every xmldoc to describe the
single canonical path without invoking the retired one. Should ship in the
same commit as C1 (or as a small dedicated commit). CI grep gate: `legacy mode|layout mode`.

Severity: **1.0 CLEANUP**. Zero runtime impact; new-contributor cost.

### C3 — `SaveBootstrap.cs` internal names use `_xxxAdapter` (naming only)

**Pattern**: (potentially #1 adapter naming, but non-violating on inspection)

- `Assets/Scripts/CombatView/SaveBootstrap.cs:64-67,106-118`

```csharp
private NodeMapSerializable _nodeMapAdapter;

private RunDeckSerializable _runDeckAdapter;
private VehicleStateSerializable _vehicleStateAdapter;
```

**Why flagged**: The `Adapter` suffix in the field name matches Pattern #1
naming, but on read, the class it names (e.g. `VehicleStateSerializable`) is
a live-model → wire-DTO projection whose xmldoc explicitly says (verbatim
from `VehicleStateSerializable.cs:19-26`):

> Why the adapter rather than registering VehicleStateDto directly: same
> **ADR-0011 #3 reasoning** as the seed / deck adapters. The DTO is a pure
> wire shape […]; the adapter owns the live-source projection. Without this
> split the DTO would carry two modes (pure wire vs live-attached snapshot),
> which is the bimodal-path anti-pattern.

**This is exempt on inspection** — the "adapter" here is the ADR-0011 escape
from a bimodal DTO, not an ADR-0011 violation. But the field-naming reads as
a violation on first grep, so recommend renaming to avoid future auditor
churn.

**Recommended fix**: Cosmetic — rename the four `_xxxAdapter` fields to
`_xxxSerializable` (matching the class name). Optional. Do not delete the
namespace; it's structurally load-bearing.

Severity: **1.0 CLEANUP**, optional.

## EXEMPT (flagged pattern, but ADR-0011 exception applies)

### E1 — `WastelandRun.Save.Adapters` namespace (~7 files + tests)

- `Assets/Scripts/Save/Adapters/*.cs` (`NodeMapSerializable`, `RunSeedSerializable`,
  `RunDeckSerializable`, `VehicleStateSerializable`)
- `Assets/Tests/EditMode/Save/*.cs` referencing the namespace

**Why exempt**: These are **not** adapter-pattern bridges. Each file is a live-source
projection component that:
- Owns a `Func<TSource>` closure to whatever `RunController` publishes.
- Implements `IRunStateSerializable.ToDto()` by projecting current source state to a fresh DTO.
- On load, captures the loaded DTO into `LastLoaded` for the resume branch to read.

This is polymorphism + composition (ADR-0011 allowed pattern #4 "Polymorphism
and strategy patterns chosen for legitimate design reasons"). The alternative
(putting a live-source closure inside the DTO class) would create the exact
bimodal-DTO shape ADR-0011 forbids — which is why the split exists. The
`VehicleStateSerializable.cs` xmldoc names ADR-0011 as its own rationale.

Verdict: EXEMPT. No change required beyond the cosmetic naming in C3.

### E2 — `BiomeWebGenerator.cs:691` `"Bridges the visual↔graph adjacency gap"`

- `Assets/Scripts/Run/BiomeWebGenerator.cs:691`

**Why exempt**: The word "bridges" appears in an English-language description of
a Delaunay-edge re-add algorithm (`"Bridges the visual ↔ graph adjacency gap
caused by stochastic forward-bias rolls"`). It is not an adapter layer between
vocabularies; it is describing what the algorithm does to the graph.
Verdict: EXEMPT.

### E3 — `RunSceneHost.HandleRestModelCommitted` "Synchronous bridge from…"

- `Assets/Scripts/CombatView/RunSceneHost.cs:653`

**Why exempt**: The word "bridge" is used to describe an event-forwarder from
`RunSession.OnRestModelCommitted` → `EnqueueRunStateSnapshot`. Standard C#
event glue, single-path, single-vocabulary. Not an ADR-0011 adapter.
Verdict: EXEMPT. Optional: rename the word "bridge" out of the xmldoc to
reduce future audit noise.
