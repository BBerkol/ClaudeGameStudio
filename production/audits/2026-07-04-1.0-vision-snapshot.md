# Wasteland Run — 1.0 Vision Snapshot

## 1. What 1.0 means

**Everything is final. All 3 biomes fully playable end-to-end.**

1.0 is the shipping game — every system, every screen, every meta-layer surface, every biome, every enemy, every encounter — in final form. A player can launch, pick a chassis, cross biome 1 → biome 2 → biome 3, arrive at Haven, and see their mastery XP apply. No content is deferred to post-launch. Post-launch work is patches, polish, balance passes, and (optional) additional content beyond the shipping arc — never core-loop completion.

## 2. Player experience arc (single run, ~90 min across 3 biomes)

1. **Main Menu** (final meta layer) — chassis pick, mastery screen visible, new-run flow.
2. **Run start** — chassis selected, starter deck loaded, tank fueled to chassis-multiplier max.
3. **Biome 1 map** — Wasteland (or biome-1 theme). Web layout, deterministic from `RunSeed`, all 6 beacon types + terminal transition to biome 2.
4. **Biome-1 beacons** — Combat, Elite Combat, Rest, Merchant, Chopshop, Event. Enemy roster: Dune Skimmer, Iron Shepherd, Dredge boss (or biome-1 terminal encounter).
5. **Biome 1 → Biome 2 transition** — terminal beacon (per `BiomeDistributionSO.TerminalBeaconType`) hands off; biome-2 map + roster load.
6. **Biome 2 map + beacons** — biome-2 distribution, biome-2 enemy roster, biome-2 events / merchant inventory / chopshop offers.
7. **Biome 2 → Biome 3 transition** — same shape.
8. **Biome 3 map + beacons** — biome-3 distribution, biome-3 enemy roster, biome-3 final boss.
9. **Haven** — endpoint, philosophical loop text, mastery XP applied, back to Main Menu.
10. **Mastery screen** — XP progression per chassis, unlocks visible, next-run seed.

Fuel-as-clock storm counter (30 steps) is calibrated for a full 3-biome run — ~10 steps per biome — and the pressure genuinely mounts as the player crosses biomes.

## 5. Architecture invariants for biome authoring

Every biome slots into these invariants — biome 1 today, biomes 2/3 during content authoring. The audit target is: does biome 1's implementation respect these? If yes, biomes 2/3 are pure authoring. If no, that's a 1.0 blocker.

1. **Biome data is a table, not a branch** (ADR-0015 pattern). New biome = new `BiomeDistributionSO` + enemy roster asset + node-layout asset. No `if (biomeId == 2)` code paths.
2. **Enemy authoring is data-driven end-to-end** — `PartDefinitionSO` (ADR-0012) + `EnemyArchetypeDefinitionSO` (Sweep B B1 remediation) + prefab. Adding a biome-2 enemy = author assets, ship.
3. **Save schema is versioned per-DTO** (ADR-0004). Adding biome-2 mastery unlocks bumps `SchemaVersion` on `MasteryStateDto` (Sweep B B4 — must land); other DTOs unaffected.
4. **Beacon type handlers are canonical vertical slices** (ADR-0015). All 6 beacon-type slices ship at 1.0. Biome-2/3 content plugs into existing handlers via SO narrowing (biome-specific merchant inventory, chopshop offers, event pool).
5. **No bridges anywhere** (ADR-0011). Zero adapter/legacy/bimodal paths. If the audit finds one, it's a 1.0 blocker.
6. **Determinism holds across biomes** (ADR-0003). `RunSeed ^ stepIndex` seeding must work identically whether the seed generates biome-1 or biome-3 content. Verified `RunController.Derive*Seed` is biome-agnostic (Sweep B K5).
7. **Biome transition is state-preserving** (new invariant for 3-biome scope). Cross-biome handoff: RunState persists, RunDeck persists, VehicleState persists, RunSeed persists. Only `NodeMap` regenerates (against derived biome-N seed).

If the codebase-health audit finds systems that violate any of these invariants, those become **1.0 blockers**, not post-1.0 cleanup.

## 6. Per-pillar success criteria at 1.0

| Pillar | 1.0 Criterion (testable across all 3 biomes) |
|---|---|
| **Vehicle as Character** | Player can identify at a glance which slot broke and which cards were granted by it. Slot Offline greys cards; scrap sweeps deck+hand+discard atomically. |
| **Chassis Identity** | Playtesting: three testers on the 3 chassis cannot converge on one dominant build across a full 3-biome run. Each chassis has ≥1 archetype non-viable on the other two. Biome-to-biome viability shifts are acceptable; strict dominance across all 3 is not. |
| **Read to Win** | Enemy intent (target + magnitude + subsystem) is legible before player commits a card. No hover-only info. Legibility holds across all 3 biomes' enemy rosters. |
| **Scarcity with Agency** | Fuel is spent per traversal; storm clock creates forward pressure that meaningfully accelerates across the 3-biome run; player always has ≥1 route decision that trades fuel for reward. Storm-clock pressure calibrated to the full ~30-step run. |
| **Route Reflects Vehicle State** | ≥1 node type is gated by vehicle state (e.g., offline Mobility locks Elite). Player sees gate reason in map UI. |
